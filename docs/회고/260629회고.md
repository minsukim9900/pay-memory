# Entity 방어 로직에서 다시 정리한 Error와 Exception의 차이

## Error와 Exception을 다시 정리하게 된 이유

페이메모리 프로젝트를 진행하면서 최근 핵심 도메인 `Entity`와 MongoDB `Document`를 구성했습니다.  
처음에는 도메인 구조를 잡고, 연관관계를 정리하고, `nullable = false`로 선언한 필드들이 잘 저장될 수 있도록 만드는 데 집중했습니다.

그런데 작업을 이어가다 보니 한 가지 고민이 생겼습니다.

`nullable = false`는 DB 레벨에서의 제약에 가깝습니다.  
물론 JPA Entity에서 해당 설정을 통해 컬럼 제약을 표현할 수 있지만, 애플리케이션 코드 안에서 객체가 생성되거나 변경되는 순간에는 여전히 잘못된 값이 들어올 가능성이 있습니다.

그래서 Entity 내부에 필수 값에 대한 방어 검증 로직을 추가했습니다.  
예를 들어 필수 필드가 `null`이면 객체가 만들어지지 않도록 하고, 금액처럼 도메인 규칙이 있는 값은 잘못된 상태로 들어오지 못하게 막았습니다.

<br>

이후 `User`, `TransactionCategory`, `PaymentTransaction`, `AiChatRoom`, `AiChatMessage`에 대한 순수 단위 테스트를 작성했습니다.  
여기서 말하는 순수 단위 테스트는 `@SpringBootTest`나 `@DataJpaTest`를 사용하지 않고, Spring Context나 DB 없이 Entity 내부 메서드만 검증하는 테스트였습니다.

처음에는 단순히 이렇게 생각했습니다.

> 잘못된 값이 들어오면 예외가 발생하면 된다.

그런데 테스트를 작성하면서 생각보다 확인해야 할 지점이 많았습니다.

특히 예외 테스트에서 AssertJ의 `catchThrowable()`을 사용해 `given`, `when`, `then` 구조를 분리하고, 예외가 발생했는지만 보는 것이 아니라 **예외 타입과 예외 메시지까지 함께 검증**했습니다.

그러다 보니 자연스럽게 이런 부분을 다시 보게 되었습니다.

```java
Objects.requireNonNull(value, "필수 값입니다.");
```

위 코드는 값이 `null`일 때 `NullPointerException`을 발생시킵니다.

반면 아래처럼 직접 작성하면,

```java
if (value == null) {
    throw new IllegalArgumentException("필수 값입니다.");
}
```

`IllegalArgumentException`이 발생합니다.

<br>

이 차이를 테스트에서 직접 마주하니, 단순히 “에러가 난다”라고 표현하고 넘어갈 수 없겠다고 느꼈습니다.  
Java에서 말하는 `Error`와 `Exception`은 분명히 다른 개념이고, Entity 내부 방어 로직에서 발생시키는 것은 `Error`가 아니라 잘못된 도메인 상태를 빠르게 발견하기 위한 `Exception`에 가깝기 때문입니다.

## Java에서 Throwable, Error, Exception의 관계

Java에서 예외와 오류를 이야기할 때 가장 위에 있는 타입은 `Throwable`입니다.  
말 그대로 Java에서 `throw` 될 수 있는 객체의 최상위 타입입니다.

구조를 단순하게 보면 다음과 같습니다.

```text
Throwable
 ├─ Error
 │   ├─ OutOfMemoryError
 │   └─ StackOverflowError
 │
 └─ Exception
     ├─ RuntimeException
     │   ├─ IllegalArgumentException
     │   ├─ NullPointerException
     │   └─ IllegalStateException
     │
     ├─ IOException
     └─ SQLException
```

<br>

`Throwable` 아래에는 크게 `Error`와 `Exception`이 있습니다.

`Error`는 일반적으로 애플리케이션 코드에서 잡아서 처리하기보다 JVM 또는 시스템 수준에서 발생하는 심각한 문제를 의미합니다.  
예를 들어 `OutOfMemoryError`는 JVM이 사용할 메모리가 부족한 상황이고, `StackOverflowError`는 호출 스택이 한계를 넘은 상황입니다.

반면 `Exception`은 애플리케이션 코드 안에서 예상하거나 처리할 수 있는 문제를 표현할 때 사용됩니다.  
예를 들어 잘못된 인자가 전달되면 `IllegalArgumentException`, `null`이면 안 되는 값이 `null`로 들어오면 `NullPointerException`, 파일 입출력 중 문제가 생기면 `IOException`, DB 처리 중 문제가 생기면 `SQLException`이 발생할 수 있습니다.


이번 작업에서 이 차이가 중요했던 이유는 Entity 방어 로직의 목적 때문이었습니다.

Entity 내부 검증은 JVM이 더 이상 동작하기 어려운 상황을 표현하는 것이 아닙니다.  
잘못된 요청이나 잘못된 생성 로직 때문에 도메인 객체가 유효하지 않은 상태로 만들어지는 것을 막기 위한 코드입니다.

즉, 페이메모리 프로젝트에서 Entity 내부에 작성한 검증 로직은 `Error`를 다루는 코드가 아니라, 애플리케이션 흐름 안에서 잘못된 상태를 발견하기 위한 `Exception`을 다루는 코드라고 보는 것이 더 정확했습니다.

## Error는 복구하기 어려운 문제에 가깝다

`Error`는 개발자가 일반적인 비즈니스 로직에서 의도적으로 던지고, 세밀하게 잡아서 처리하는 대상으로 보기는 어렵습니다.

예를 들어 서버에서 `OutOfMemoryError`가 발생했다고 가정해보겠습니다.  
이 상황은 사용자가 금액을 잘못 입력했거나, 필수 값을 누락했다는 수준의 문제가 아닙니다. JVM이 객체를 더 이상 할당하기 어려운 상태에 가까우며, 애플리케이션이 정상적으로 요청을 처리할 수 있는 기반 자체가 흔들리는 상황입니다.

`StackOverflowError`도 마찬가지입니다.  
재귀 호출이 끝나지 않거나, 객체 간 호출 구조가 잘못되어 호출 스택이 계속 쌓이다가 한계를 넘을 때 발생할 수 있습니다. 이 역시 특정 도메인 규칙 위반을 처리하는 예외라기보다는 코드 구조나 실행 환경을 점검해야 하는 문제에 가깝습니다.

<br>

물론 모든 상황에서 `Error`를 절대 `catch`하면 안 된다고 단정하고 싶지는 않습니다.  
특정 프레임워크나 라이브러리, 혹은 매우 제한된 시스템 코드에서는 특별한 목적을 가지고 다룰 수도 있습니다.

다만 일반적인 Spring Boot 애플리케이션의 비즈니스 로직 안에서는 `Error`를 처리 대상으로 두기보다, 발생 원인을 분석하고 시스템 설정, 메모리 사용량, 코드 구조, 배포 환경 등을 점검해야 하는 문제로 바라보는 편이 자연스럽다고 느꼈습니다.

그래서 Entity 내부에서 필수 값이 누락되었거나 금액이 잘못된 상황을 `Error`로 표현하는 것은 맞지 않습니다.  
그런 상황은 시스템이 무너진 것이 아니라, 애플리케이션 흐름 안에서 잘못된 도메인 상태가 만들어지려는 것이기 때문입니다.

---

## Exception은 애플리케이션 흐름 안에서 다룰 수 있는 문제다

`Exception`은 애플리케이션 코드 안에서 예상 가능한 문제를 표현하는 데 사용됩니다.

예를 들어 사용자가 잘못된 값을 보냈을 수 있습니다.  
존재하지 않는 데이터를 조회했을 수도 있습니다.  
또는 도메인 객체가 유효하지 않은 상태로 생성되려는 상황도 있을 수 있습니다.

이런 문제들은 JVM이 더 이상 동작할 수 없는 상황이라기보다, 애플리케이션이 처리 흐름 안에서 발견하고 대응할 수 있는 문제에 가깝습니다.

<br>

Spring Boot 프로젝트를 진행하다 보면 예외를 여러 계층에서 마주하게 됩니다.  
이번 페이메모리 프로젝트에서는 대략 다음 기준으로 나누어 생각했습니다.

### DTO Validation

DTO Validation은 사용자 입력을 검증하는 역할에 가깝습니다.

예를 들어 요청 Body로 들어온 값이 비어 있거나, 형식이 맞지 않거나, 길이 제한을 넘는 경우가 여기에 해당합니다.

```java
@NotBlank(message = "사용처는 필수입니다.")
private String merchantName;
```

이런 검증은 클라이언트에게 전달할 수 있는 검증 메시지와 연결되기 쉽습니다.  
사용자가 어떤 값을 잘못 보냈는지 알려주는 목적이 강하기 때문입니다.

<br>

### Entity 내부 검증

Entity 내부 검증은 도메인 객체의 유효한 상태를 보호하는 역할을 합니다.

DTO에서 한 번 검증했다고 해서 Entity가 항상 안전하다고 볼 수는 없습니다.  
테스트 코드에서 직접 Entity를 생성할 수도 있고, Service 내부에서 조합된 값으로 Entity를 만들 수도 있으며, 나중에 다른 기능이 추가되면서 예상하지 못한 경로로 객체가 생성될 수도 있습니다.

그래서 Entity는 스스로 최소한의 도메인 규칙을 지키고 있어야 한다고 생각했습니다.

Entity 내부 검증의 목적은 사용자에게 친절한 메시지를 내려주는 것보다, 잘못된 객체 생성이나 수정을 빠르게 발견하는 데 더 가깝습니다.

<br>

### Service 비즈니스 예외

Service 계층에서는 조금 더 비즈니스 흐름에 가까운 예외가 발생합니다.

예를 들어 존재하지 않는 사용자를 조회하거나, 권한이 없는 요청을 처리하려 하거나, 이미 처리된 요청이 다시 들어오는 경우가 있습니다.

이런 예외는 단순히 값 하나가 `null`인지 아닌지를 넘어서, 서비스의 규칙을 위반한 상황입니다.  
따라서 프로젝트의 공통 예외 구조나 도메인별 예외 코드와 연결하기 좋습니다.

## Entity 방어 로직에서 사용한 Exception

페이메모리 프로젝트에서는 Entity 내부에 필수 값과 도메인 규칙을 검증하는 방어 로직을 추가했습니다.  
그중 `PaymentTransaction`은 거래 내역을 표현하는 핵심 도메인이라, 객체가 잘못된 상태로 생성되지 않도록 검증 기준을 분명히 둘 필요가 있었습니다.

예를 들어 거래 카테고리, 거래일시, 사용처, 금액, 거래 유형은 거래 내역을 구성하는 데 필요한 값입니다.  
이 값들이 비어 있거나 잘못되면 `PaymentTransaction` 객체 자체가 의미 있는 거래 내역이라고 보기 어렵습니다.

그래서 다음과 같은 검증 메서드를 두었습니다.

```java
private void validateTransactionFields(
        TransactionCategory transactionCategory,
        Instant transactionAt,
        String merchantName,
        long amount,
        TransactionType transactionType
) {
    Objects.requireNonNull(transactionCategory, "거래 카테고리는 필수입니다.");
    Objects.requireNonNull(transactionAt, "거래일시는 필수입니다.");
    Objects.requireNonNull(transactionType, "거래 유형은 필수입니다.");
    if (merchantName == null || merchantName.isBlank()) {
        throw new IllegalArgumentException("사용처는 필수입니다.");
    }
    if (amount <= 0) {
        throw new IllegalArgumentException("금액은 0보다 커야 합니다.");
    }
}
```

<br>

이 코드는 `Error`를 발생시키기 위한 코드가 아닙니다.  
JVM이 더 이상 실행되기 어렵다거나, 시스템 리소스가 부족하다는 의미도 아닙니다.

이 코드는 잘못된 도메인 상태를 막기 위해 `Exception`을 발생시키는 코드입니다.

`transactionCategory`, `transactionAt`, `transactionType`은 `Objects.requireNonNull()`을 사용했기 때문에 값이 `null`이면 `NullPointerException`이 발생합니다.

반면 `merchantName`과 `amount`는 직접 조건문을 작성해 `IllegalArgumentException`을 던졌습니다.  
그래서 테스트에서도 `merchantName`이 `blank`일 때는 `IllegalArgumentException`이 발생하는지 검증했고, `amount`가 `0` 이하일 때도 같은 타입으로 검증했습니다.

<br>

처음에는 “필수 값이 없으면 예외가 발생한다” 정도로만 봤는데, 테스트를 작성하다 보니 어떤 코드가 어떤 예외 타입을 발생시키는지까지 명확히 알아야 했습니다.  
`Objects.requireNonNull()`을 사용한 필드와 직접 `throw new IllegalArgumentException()`을 작성한 필드는 테스트에서 기대해야 하는 예외 타입이 달랐기 때문입니다.

## NullPointerException은 무조건 나쁜 예외일까?

`NullPointerException`은 보통 좋지 않은 신호로 받아들여집니다.

예를 들어 어떤 객체가 `null`인지 모르고 메서드를 호출하다가 발생하는 NPE는 예상하지 못한 오류에 가깝습니다.

```java
user.getName();
```

위 코드에서 `user`가 `null`인데 `getName()`을 호출하면 `NullPointerException`이 발생합니다.  
이런 경우는 대체로 코드가 null 가능성을 충분히 다루지 못했다는 신호로 볼 수 있습니다.

<br>

하지만 모든 `NullPointerException`이 같은 의미를 갖는 것은 아니라고 생각했습니다.

```java
Objects.requireNonNull(value, "필수 값입니다.");
```

위 코드는 조금 다릅니다.  
`value`가 `null`이면 안 된다는 조건을 코드에 명시하고, 그 조건을 위반했을 때 의도적으로 `NullPointerException`을 발생시킵니다.

즉, 이 경우의 NPE는 “예상하지 못한 null 접근”이라기보다 “이 값은 필수 값이고, null이면 안 된다는 조건을 명시한 NPE”에 가깝습니다.

<br>

물론 프로젝트의 예외 정책에 따라 모든 인자 검증 실패를 `IllegalArgumentException`으로 통일할 수도 있습니다.  
예를 들어 아래처럼 직접 검증하면 예외 타입을 통일할 수 있습니다.

```java
if (transactionCategory == null) {
    throw new IllegalArgumentException("거래 카테고리는 필수입니다.");
}
```

이 방식은 테스트에서 기대하는 예외 타입이 더 단순해진다는 장점이 있습니다.  
또한 “잘못된 인자가 전달되었다”는 의미를 `IllegalArgumentException`으로 통일할 수 있습니다.

다만 이번 페이메모리 프로젝트에서 Entity 방어 로직의 핵심은 예외 타입을 하나로 통일하는 것보다, Entity가 잘못된 상태로 만들어지지 않게 막는 것이었습니다.

그래서 `null` 자체를 명확하게 막고 싶은 필드는 `Objects.requireNonNull()`을 사용했고, 문자열이 비어 있거나 금액이 0 이하인 것처럼 별도의 도메인 조건이 있는 경우에는 `IllegalArgumentException`을 직접 던지는 방식으로 작성했습니다.

이 선택이 모든 프로젝트에서 정답이라고 생각하지는 않습니다.  
다만 현재 단계에서는 코드의 의도가 비교적 잘 드러났고, 테스트에서도 어떤 경우에 어떤 예외가 발생하는지 분명히 확인할 수 있었습니다.

## 예외 타입과 메시지를 테스트한 이유

이번 단위 테스트에서는 단순히 “예외가 발생한다”만 확인하지 않았습니다.  
예외 타입과 메시지를 함께 검증했습니다.

예를 들어 `PaymentTransaction`에서 `merchantName`이 blank인 경우에는 다음과 같이 테스트했습니다.

```java
@Test
@DisplayName("merchantName이 blank이면 예외가 발생한다.")
void throwExceptionWhenMerchantNameIsBlank() throws Exception {
    //given
    String merchantName = " ";
    //when
    Throwable thrown = catchThrowable(() ->
            createPaymentTransactionWithMerchantName(merchantName)
    );
    //then
    assertThat(thrown)
            .isInstanceOf(IllegalArgumentException.class)
            .hasMessage("사용처는 필수입니다.");
}
```

<br>

이 테스트를 작성하면서 좋았던 점은, Entity가 가진 규칙이 테스트 코드 안에 비교적 선명하게 남는다는 것이었습니다.

`merchantName`이 비어 있으면 예외가 발생해야 한다는 것뿐만 아니라, 그 예외가 `IllegalArgumentException`이어야 하고 메시지는 `"사용처는 필수입니다."`여야 한다는 점까지 확인할 수 있었습니다.

이렇게 작성해두면 나중에 검증 로직이 바뀌었을 때도 테스트가 기준 역할을 해줍니다.  
누군가 `merchantName` 검증을 제거하거나, 메시지를 바꾸거나, 예외 타입을 다르게 변경하면 테스트가 실패합니다.

물론 예외 메시지까지 테스트하면 메시지 변경에 테스트가 민감해질 수 있습니다.  
하지만 Entity 내부의 도메인 규칙을 명확히 남기고 싶은 상황에서는 메시지 검증도 의미가 있다고 느꼈습니다.

<br>

또한 `catchThrowable()`을 사용하니 `given`, `when`, `then` 구조가 깔끔하게 나뉘었습니다.

```java
//given
String merchantName = " ";

//when
Throwable thrown = catchThrowable(() ->
        createPaymentTransactionWithMerchantName(merchantName)
);

//then
assertThat(thrown)
        .isInstanceOf(IllegalArgumentException.class)
        .hasMessage("사용처는 필수입니다.");
```

예외가 발생하는 코드를 `when` 영역에서 명확히 분리할 수 있었고, `then`에서는 발생한 예외를 대상으로 타입과 메시지를 검증할 수 있었습니다.

이번 테스트를 작성하면서 테스트 코드는 단순히 코드가 맞는지 확인하는 도구를 넘어서, Entity가 어떤 도메인 규칙을 가지고 있는지 보여주는 문서 역할도 한다고 느꼈습니다.

## Checked Exception과 Unchecked Exception도 함께 정리

`Exception` 안에서도 다시 `Checked Exception`과 `Unchecked Exception`으로 나눌 수 있습니다.

### Checked Exception

`Checked Exception`은 컴파일 시점에 처리 여부를 강제하는 예외입니다.  
즉, 해당 예외가 발생할 수 있는 코드를 작성하면 `try-catch`로 잡거나, 메서드 선언부에 `throws`로 넘겨야 합니다.

대표적인 예시는 다음과 같습니다.

```java
IOException
SQLException
```

파일을 읽거나 쓰는 과정에서 문제가 생길 수 있고, DB와 통신하는 과정에서도 문제가 생길 수 있습니다.  
이런 예외는 호출하는 쪽에서 처리하거나 상위로 넘기도록 컴파일러가 강제합니다.

<br>

### Unchecked Exception

`Unchecked Exception`은 `RuntimeException` 계열의 예외입니다.  
컴파일러가 처리 여부를 강제하지 않습니다.

대표적인 예시는 다음과 같습니다.

```java
IllegalArgumentException
NullPointerException
IllegalStateException
```

잘못된 인자가 전달되었거나, `null`이면 안 되는 값이 `null`이거나, 객체 상태가 메서드를 실행하기에 적절하지 않은 경우에 사용할 수 있습니다.

<br>

Entity 내부 방어 로직에서는 보통 `Checked Exception`보다 `Unchecked Exception`을 사용하는 흐름이 더 자연스럽다고 생각했습니다.

Entity를 생성하거나 상태를 변경하는 과정에서 잘못된 호출이 들어왔다면, 그것은 호출한 코드가 도메인 규칙을 어긴 상황입니다.  
이런 경우 매번 `try-catch`를 강제하기보다는, 잘못된 호출을 빠르게 드러내고 테스트나 개발 과정에서 바로 확인할 수 있게 만드는 편이 더 적절하다고 느꼈습니다.

예를 들어 `PaymentTransaction`을 생성할 때 금액이 0 이하라면, 그 객체는 애초에 유효한 거래 내역이라고 보기 어렵습니다.  
이 상황을 `Checked Exception`으로 만들어 매번 호출부에서 처리하게 하기보다는, `IllegalArgumentException`으로 빠르게 실패시키는 방식이 Entity 방어 로직의 목적과 더 잘 맞았습니다.

## Spring 프로젝트에서 예외를 계층별로 바라본 기준

페이메모리 프로젝트에는 공통 예외 구조도 있습니다.  
Service 계층에서는 `GeneralException`과 도메인 Exception Enum을 사용해 비즈니스 예외를 표현하는 흐름을 잡고 있습니다.

그렇다고 해서 Entity 내부에서 발생하는 모든 예외까지 무조건 커스텀 예외로 감싸는 것이 항상 좋은 선택이라고 보지는 않았습니다.

이번 프로젝트에서는 예외를 계층별로 다음과 같이 바라보는 편이 더 단순하고 명확했습니다.

<br>

### Request DTO

Request DTO에서는 Bean Validation을 사용합니다.

```java
@NotBlank
@NotNull
@Positive
```

이 영역은 사용자 입력 오류를 처리하는 데 가깝습니다.  
클라이언트가 잘못된 값을 보냈다면 어떤 필드가 왜 잘못되었는지 알려줄 수 있어야 합니다.

따라서 Request DTO의 검증은 사용자에게 전달할 수 있는 메시지와 연결됩니다.

<br>

### Entity

Entity에서는 `IllegalArgumentException`, `NullPointerException` 같은 기본 런타임 예외를 사용했습니다.

이 영역의 목적은 잘못된 도메인 상태를 방어하는 것입니다.  
Entity가 생성되는 순간부터 최소한의 유효성을 지키도록 만들고, 잘못된 값이 들어오면 빠르게 실패하게 했습니다.

Entity 내부 예외는 클라이언트 응답을 직접 만들기 위한 예외라기보다, 도메인 객체가 스스로 지켜야 하는 규칙을 어겼다는 신호에 가깝다고 봤습니다.

<br>

### Service

Service 계층에서는 `GeneralException`과 도메인 Exception Enum을 사용해 비즈니스 규칙 위반을 처리합니다.

예를 들면 다음과 같은 상황입니다.

```text
존재하지 않는 사용자
권한 없음
중복 요청
이미 삭제된 데이터
허용되지 않은 상태 변경
```

이런 예외는 사용자 응답과도 연결될 수 있고, API 에러 코드로 관리할 필요도 있습니다.  
그래서 공통 예외 구조를 적용하기에 적절한 위치라고 생각했습니다.

<br>

### ControllerAdvice

`ControllerAdvice`에서는 발생한 예외를 공통 응답 형식으로 변환합니다.

DTO Validation에서 발생한 예외든, Service에서 발생한 비즈니스 예외든, 최종적으로 클라이언트에게는 프로젝트에서 정한 응답 포맷으로 내려가야 합니다.

이 계층은 예외를 직접 발생시키는 곳이라기보다, 발생한 예외를 HTTP 응답으로 변환하는 역할에 가깝습니다.

<br>

정리하면 이번 프로젝트에서는 다음 기준을 사용했습니다.

```text
Request DTO
 → Bean Validation
 → 사용자 입력 오류 처리

Entity
 → IllegalArgumentException, NullPointerException 등 기본 런타임 예외
 → 잘못된 도메인 상태 방어

Service
 → GeneralException + 도메인 Exception Enum
 → 비즈니스 규칙 위반 처리

ControllerAdvice
 → 예외를 공통 응답 형식으로 변환
```

프로젝트에 공통 예외 구조가 있다고 해서 Entity 내부 예외까지 모두 커스텀 예외로 감싸면 오히려 기준이 흐려질 수 있다고 느꼈습니다.

현재 단계에서는 Entity 내부 검증은 기본 런타임 예외로 두고, 사용자 응답과 직접 관련된 예외는 DTO Validation과 Service 비즈니스 예외에서 처리하는 기준이 더 단순했습니다.

나중에 Entity 예외도 공통 응답 정책과 더 강하게 연결해야 하는 요구가 생긴다면 그때 다시 조정할 수 있겠지만, 지금은 Entity가 잘못된 상태로 만들어지지 않도록 막는 것에 집중하는 편이 더 맞다고 생각했습니다.

## 이번 작업을 통해 배운 점

이번 작업을 통해 가장 먼저 정리한 것은 `Error`와 `Exception`을 단순히 “에러”라는 말로 뭉뚱그려 쓰면 안 된다는 점이었습니다.

개발하면서 흔히 “에러가 났다”라고 말하지만, Java 타입 구조 안에서 `Error`와 `Exception`은 분명히 다릅니다.

`Error`는 JVM이나 시스템 수준에서 애플리케이션이 정상적으로 복구하기 어려운 문제에 가깝습니다.  
반면 `Exception`은 애플리케이션 흐름 안에서 예상하거나 처리할 수 있는 문제를 표현합니다.

페이메모리 프로젝트에서 Entity 내부 방어 로직으로 발생시키는 것은 `Error`가 아닙니다.  
필수 값이 누락되었거나, 잘못된 값으로 도메인 객체가 생성되려는 상황을 빠르게 발견하기 위한 `Exception`입니다.

<br>

또한 `Exception`도 하나로만 보면 부족하다는 것을 다시 느꼈습니다.

`Checked Exception`과 `Unchecked Exception`이 있고, 사용자 입력 검증 예외와 비즈니스 예외도 목적이 다릅니다.  
Entity 내부 검증에서 사용하는 예외와 Service 계층에서 사용하는 도메인 예외도 같은 기준으로 볼 수는 없었습니다.

이번 테스트를 작성하면서 예외 타입을 정확히 알고 있어야 테스트도 정확히 작성할 수 있다는 점을 확인했습니다.

특히 `Objects.requireNonNull()`이 `NullPointerException`을 발생시킨다는 점을 테스트 작성 과정에서 명확히 다시 보게 되었습니다.  
반대로 직접 `throw new IllegalArgumentException()`을 작성한 경우에는 당연히 `IllegalArgumentException`을 기대해야 했습니다.

이 차이를 알고 나니 테스트 코드도 더 분명해졌습니다.

```java
assertThat(thrown)
        .isInstanceOf(NullPointerException.class)
        .hasMessage("거래 카테고리는 필수입니다.");
```

```java
assertThat(thrown)
        .isInstanceOf(IllegalArgumentException.class)
        .hasMessage("사용처는 필수입니다.");
```

두 테스트는 모두 “잘못된 값이면 예외가 발생한다”는 점에서는 같지만, 코드가 표현하는 의미와 기대하는 예외 타입은 다릅니다.

이런 부분을 테스트로 확인해두니 Entity 내부 검증 로직이 조금 더 명확한 기준을 갖게 되었다고 느꼈습니다.

## 정리하면

이번 페이메모리 프로젝트에서 Entity와 MongoDB Document를 구성하고, Entity 내부 방어 로직과 순수 단위 테스트를 작성하면서 Java 예외 구조를 다시 정리하게 되었습니다.

처음에는 단순히 “잘못된 값이면 예외가 발생한다” 정도로 생각했지만, 테스트에서 예외 타입과 메시지를 직접 검증하다 보니 `Error`, `Exception`, `NullPointerException`, `IllegalArgumentException`의 차이를 분명히 알고 있어야 했습니다.

정리하면 다음과 같습니다.

```text
Error는 애플리케이션이 정상적으로 복구하기 어려운 시스템 수준의 문제에 가깝다.

Exception은 애플리케이션 흐름 안에서 예상하거나 처리할 수 있는 문제를 표현한다.

Entity 내부 방어 로직은 잘못된 도메인 상태를 막기 위한 Exception으로 볼 수 있다.

예외 타입과 메시지를 테스트하면 도메인 객체의 규칙을 더 명확히 확인할 수 있다.
```

<br>

이번 작업을 통해 Entity 테스트는 단순히 생성자가 잘 동작하는지 확인하는 테스트가 아니라는 생각이 들었습니다.  
Entity가 어떤 상태를 허용하고, 어떤 상태를 거부하는지 보여주는 가장 가까운 문서가 될 수 있었습니다.

그리고 예외를 테스트한다는 것은 단순히 실패 케이스를 확인하는 일이 아니라, 도메인 객체가 지켜야 할 선을 코드로 남기는 작업에 가깝다고 느꼈습니다.

앞으로 Service 계층의 비즈니스 예외를 정리할 때도 이번에 세운 기준을 이어갈 수 있을 것 같습니다.  
DTO Validation은 사용자 입력 검증, Entity 내부 검증은 도메인 상태 보호, Service 예외는 비즈니스 규칙 위반 처리라는 기준을 유지하면 예외 구조가 더 복잡해지더라도 역할을 나누어 바라볼 수 있을 것 같습니다.
