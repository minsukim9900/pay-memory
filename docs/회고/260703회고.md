# Spring Security 필터 단계의 예외는 왜 GlobalExceptionHandler에서 잡히지 않을까?

![예외 처리 책임 분리 요약](https://velog.velcdn.com/images/mindoli/post/0a101e8c-e9d5-476f-ae29-ac984fc42b1f/image.png)

프로젝트에서 API 응답 형식을 맞추다 보면 자연스럽게 전역 예외 처리 구조를 만들게 됩니다.

PayMemory 프로젝트도 마찬가지였습니다.  
Controller나 Service에서 발생하는 예외는 `GlobalExceptionHandler`에서 처리하고, 클라이언트에는 항상 같은 JSON 형식으로 응답하도록 구성했습니다.

그런데 인증 실패 응답을 공통화하는 과정에서 예상과 다른 상황을 만났습니다.

Access Token이 없는 상태로 인증이 필요한 API를 호출했는데, 기존에 만들어둔 `GlobalExceptionHandler`가 동작하지 않았습니다.  
Controller나 Service 예외는 잘 잡히는데, Spring Security 인증 실패만 다른 흐름으로 처리되고 있었습니다.

처음에는 `GlobalExceptionHandler`가 이름 그대로 전역 예외를 모두 처리할 것이라고 생각했습니다.  
하지만 원인을 따라가 보니 그렇지 않았습니다.

> GlobalExceptionHandler는 모든 예외를 처리하는 만능 Handler가 아니었습니다.

이번 글에서는 PayMemory 프로젝트에서 인증/인가 실패 응답을 공통화하면서 마주친 문제를 바탕으로, 왜 Spring Security 필터 단계의 예외가 `GlobalExceptionHandler`에서 잡히지 않는지 정리합니다.

---

## 문제 상황

PayMemory는 Spring Boot 기반 백엔드 프로젝트입니다.  
인증은 Kakao OAuth2 로그인과 JWT를 기반으로 구성했습니다.

현재 인증 흐름은 다음과 같습니다.

```text
Kakao OAuth2 로그인
→ 사용자 조회 또는 생성
→ Access Token 발급
→ Refresh Token 발급
→ Access Token은 HttpOnly Cookie로 응답
→ Refresh Token도 HttpOnly Cookie로 응답
→ Refresh Token은 SHA-256 해시 후 Redis에 저장
```

응답 형식은 프로젝트 전역에서 `ResponseBody`를 사용해 통일하고 있습니다.

성공 응답은 다음과 같은 형태입니다.

```json
{
  "statusCode": 200,
  "message": "OK"
}
```

에러 응답은 다음과 같은 형태입니다.

```json
{
  "statusCode": 401,
  "message": "인증이 필요합니다.",
  "errorCode": 40104
}
```

Controller나 Service에서 비즈니스 예외가 발생하면 `GlobalExceptionHandler`가 예외를 잡고, `ResponseBody.error()`를 사용해 공통 에러 응답으로 변환합니다.

그래서 처음에는 인증 실패도 같은 방식으로 처리될 것이라고 생각했습니다.

예를 들어 Access Token이 없거나 만료된 경우 JWT 필터에서 예외가 발생하면, 그 예외가 `GlobalExceptionHandler`까지 전달되고 공통 응답으로 내려갈 것이라고 예상했습니다.

하지만 실제로는 그렇게 동작하지 않았습니다.

인증이 필요한 API를 Access Token 없이 호출하면 요청은 Controller에 도달하지 않았고, `GlobalExceptionHandler`도 실행되지 않았습니다.

문제는 예외 처리 코드가 부족한 것이 아니라, 예외가 발생한 위치였습니다.

---

Spring Boot에서 전역 예외 처리를 구현할 때 자주 사용하는 방식이 `@RestControllerAdvice`입니다.

보통 애플리케이션 요청 흐름을 다음처럼 생각합니다.

```text
Client
→ Controller
→ Service
→ Repository
```

이 흐름 안에서 예외가 발생하면 `GlobalExceptionHandler`가 예외를 잡아 공통 응답으로 변환합니다.

예를 들어 Service에서 사용자 조회에 실패해 `GlobalException`을 던진다면 다음과 같은 흐름이 됩니다.

```text
Service에서 GlobalException 발생
→ Controller 계층으로 예외 전파
→ GlobalExceptionHandler에서 처리
→ ResponseBody.error() 형태로 응답
```

이 흐름은 Controller 이후의 애플리케이션 로직에서 발생한 예외를 처리하기에 적합합니다.

하지만 Spring Security 인증 실패는 이 흐름과 위치가 다릅니다.

`@RestControllerAdvice`는 Spring MVC 영역에서 동작합니다.  
Spring 공식 문서에서도 `@Controller`와 `@ControllerAdvice`의 `@ExceptionHandler`는 Controller method에서 발생한 예외를 처리한다고 설명합니다. 또한 `@RestControllerAdvice`는 `@ControllerAdvice`에 `@ResponseBody`가 결합된 형태라고 설명합니다.

즉, `GlobalExceptionHandler`는 Spring MVC가 Controller 또는 Handler를 호출하는 흐름 안에서 발생한 예외를 처리합니다.

반대로 요청이 Controller에 도달하기 전에 막힌다면 `GlobalExceptionHandler`가 개입할 기회가 없습니다.

이번 문제도 이 지점에서 발생했습니다.

Access Token이 없는 요청은 Controller까지 도달하지 않았습니다.  
Spring Security Filter Chain에서 먼저 인증 여부를 판단했고, 인증되지 않은 요청으로 처리했습니다.

그래서 `GlobalExceptionHandler`가 실행되지 않았습니다.

> Controller 이후의 예외와 Security Filter 단계의 예외는 처리 위치가 다릅니다.

이 차이를 이해하면 문제의 원인이 조금 더 명확해집니다.

## 요청은 Controller에 도달하기 전에 Spring Security Filter Chain

![요청 흐름과 예외 처리 위치](https://velog.velcdn.com/images/mindoli/post/52fe232c-6fa5-4749-b74f-43dca6a7ff2d/image.png)

Spring Boot 애플리케이션에서 요청이 들어오면 바로 Controller가 실행되는 것처럼 느껴질 수 있습니다.

하지만 실제로는 Controller 앞에 여러 Servlet Filter가 있습니다.  
Spring Security를 사용하면 요청은 `DispatcherServlet`과 Controller에 도달하기 전에 `Spring Security Filter Chain`을 먼저 지납니다.

간단히 표현하면 다음과 같습니다.

```text
Client
→ Servlet Filter
→ Spring Security Filter Chain
→ DispatcherServlet
→ Controller
→ Service
```

Spring Security 공식 문서에서는 Servlet 기반 Spring Security 지원이 `FilterChainProxy` 안에 포함된다고 설명합니다.  
`FilterChainProxy`는 여러 Security Filter를 `SecurityFilterChain`을 통해 위임하는 특별한 Filter입니다.

또한 Spring Security의 Filter들은 인증, 인가, 보안 관련 처리를 위해 정해진 순서대로 실행됩니다.  
인증을 수행하는 Filter는 인가를 수행하는 Filter보다 앞에서 실행되어야 합니다.

이 말은 인증/인가 판단이 Controller보다 앞에서 일어난다는 뜻입니다.

예를 들어 다음 요청을 생각해볼 수 있습니다.

```text
GET /payments
Cookie에 Access Token 없음
```

`/payments`가 인증이 필요한 API라면 Spring Security는 이 요청을 Controller로 넘기기 전에 인증 여부를 확인합니다.

Access Token이 없거나, 토큰이 유효하지 않거나, `SecurityContext`에 인증 정보가 설정되지 않았다면 이 요청은 인증되지 않은 요청으로 판단됩니다.

이 시점은 아직 Controller가 실행되기 전입니다.

따라서 Controller 내부에서 예외가 발생한 것도 아니고, Service까지 진입한 것도 아닙니다.  
결과적으로 `GlobalExceptionHandler`가 처리할 수 있는 범위 밖에서 인증 실패가 발생합니다.


여기서 기존 생각을 바꿔야 했습니다.

인증/인가 실패 응답도 공통화하고 싶다면 `GlobalExceptionHandler`에만 의존하면 안 됩니다.  
Spring Security Filter Chain에서 발생하는 인증/인가 실패는 Spring Security가 제공하는 별도의 처리 지점에서 응답을 만들어야 합니다.

그 역할을 담당하는 것이 다음 두 가지입니다.

```text
인증 실패 → AuthenticationEntryPoint
인가 실패 → AccessDeniedHandler
```

Spring Security 공식 문서에서도 `ExceptionTranslationFilter`가 `AuthenticationException`과 `AccessDeniedException`을 HTTP 응답으로 변환한다고 설명합니다.

그리고 사용자가 인증되지 않았거나 `AuthenticationException`이 발생하면 `AuthenticationEntryPoint`를 사용하고, `AccessDeniedException`이 발생한 인가 실패 상황에서는 `AccessDeniedHandler`를 호출한다고 설명합니다.

## 인증 실패와 인가 실패
![인증 실패, 인가 실패](https://velog.velcdn.com/images/mindoli/post/a40b597e-7198-45fa-8d7c-4070fbbd4df6/image.png)

인증과 인가는 비슷하게 느껴지지만 서로 다른 개념입니다.

인증은 사용자가 누구인지 확인하는 과정입니다.

```text
이 요청을 보낸 사용자가 로그인한 사용자인가?
유효한 Access Token을 가지고 있는가?
SecurityContext에 Authentication이 존재하는가?
```

반면 인가는 인증된 사용자가 특정 리소스에 접근할 권한이 있는지 확인하는 과정입니다.

```text
로그인은 되어 있지만 이 API에 접근할 권한이 있는가?
관리자 권한이 필요한 API에 일반 사용자가 접근하고 있지는 않은가?
```

보통 HTTP 상태 코드 기준으로 다음처럼 구분합니다.

| 상황 | 의미 | 상태 코드 | Spring Security 처리 지점 |
| --- | --- | --- | --- |
| 인증 실패 | 로그인하지 않았거나 인증 정보가 유효하지 않음 | 401 Unauthorized | `AuthenticationEntryPoint` |
| 인가 실패 | 인증은 되었지만 접근 권한이 부족함 | 403 Forbidden | `AccessDeniedHandler` |

예를 들어 Access Token이 없는 상태로 인증이 필요한 API를 호출했다면 인증 실패입니다.

```text
Access Token 없음
→ 사용자가 누구인지 확인할 수 없음
→ 401 Unauthorized
→ AuthenticationEntryPoint 실행
```

반대로 Access Token은 유효해서 사용자가 누구인지는 확인되었지만, 관리자만 접근할 수 있는 API에 일반 사용자가 접근했다면 인가 실패입니다.

```text
Access Token 유효
→ 사용자는 인증됨
→ 하지만 권한 부족
→ 403 Forbidden
→ AccessDeniedHandler 실행
```



이 차이를 분리해두면 클라이언트에서도 실패 원인을 더 명확하게 처리할 수 있습니다.

401 응답이라면 로그인 페이지로 이동하거나 토큰 재발급을 시도할 수 있습니다.  
403 응답이라면 로그인 문제가 아니라 권한 문제이므로 접근 권한이 없다는 메시지를 보여주는 것이 더 자연스럽습니다.

> 인증 실패는 AuthenticationEntryPoint, 인가 실패는 AccessDeniedHandler가 담당합니다.

## AuthenticationEntryPoint로 인증 실패 응답 처리하기

먼저 Security 단계에서 사용할 에러 코드를 추가했습니다.

PayMemory는 기존 에러 응답도 `ErrorCode` 인터페이스를 기반으로 처리하고 있었기 때문에, Security 전용 에러 코드도 같은 구조를 따르도록 했습니다.

```java
package site.paymemory.global.security.exception;

import lombok.Getter;
import lombok.RequiredArgsConstructor;
import org.springframework.http.HttpStatus;
import site.paymemory.global.exception.ErrorCode;

@Getter
@RequiredArgsConstructor
public enum SecurityErrorCode implements ErrorCode {

    UNAUTHENTICATED_USER(
            HttpStatus.UNAUTHORIZED,
            40104,
            "인증이 필요합니다."
    ),

    ACCESS_DENIED(
            HttpStatus.FORBIDDEN,
            40301,
            "접근 권한이 없습니다."
    );

    private final HttpStatus status;
    private final int code;
    private final String message;
}
```

`UNAUTHENTICATED_USER`는 인증되지 않은 사용자를 위한 에러 코드입니다.

Access Token이 없거나 유효하지 않은 상태에서 인증이 필요한 API를 호출하면 이 응답을 내려주고 싶었습니다.

이때 필요한 것이 `AuthenticationEntryPoint`입니다.

```java
package site.paymemory.global.security.handler;

import com.fasterxml.jackson.databind.ObjectMapper;
import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;
import lombok.RequiredArgsConstructor;
import org.springframework.security.core.AuthenticationException;
import org.springframework.security.web.AuthenticationEntryPoint;
import org.springframework.stereotype.Component;
import site.paymemory.global.exception.ErrorCode;
import site.paymemory.global.response.ResponseBody;
import site.paymemory.global.security.exception.SecurityErrorCode;

import java.io.IOException;

@Component
@RequiredArgsConstructor
public class CustomAuthenticationEntryPoint implements AuthenticationEntryPoint {

    private final ObjectMapper objectMapper;

    @Override
    public void commence(
            HttpServletRequest request,
            HttpServletResponse response,
            AuthenticationException authException
    ) throws IOException {

        ErrorCode errorCode = SecurityErrorCode.UNAUTHENTICATED_USER;
        ResponseBody<Void> body = ResponseBody.error(errorCode);

        response.setStatus(errorCode.getStatus().value());
        response.setCharacterEncoding("UTF-8");
        response.setContentType("application/json");
        response.getWriter().write(objectMapper.writeValueAsString(body));
    }
}
```

여기서 중요한 점은 `ResponseEntity`를 반환하지 않는다는 점입니다.

Controller에서는 보통 다음과 같이 응답을 반환합니다.

```java
return ResponseEntity.status(status).body(body);
```

하지만 `AuthenticationEntryPoint`는 Controller가 아닙니다.  
Spring MVC Controller 메서드 안에서 실행되는 코드가 아니라, Spring Security Filter Chain 안에서 실행되는 코드입니다.

따라서 메서드 반환값으로 응답을 만드는 구조가 아닙니다.  
대신 `HttpServletResponse`에 직접 상태 코드, Content-Type, 응답 Body를 작성해야 합니다.

```java
response.setStatus(errorCode.getStatus().value());
response.setCharacterEncoding("UTF-8");
response.setContentType("application/json");
response.getWriter().write(objectMapper.writeValueAsString(body));
```

Spring Security의 `AuthenticationEntryPoint` 인터페이스 문서에서도 `commence()` 메서드는 `HttpServletRequest`, `HttpServletResponse`, `AuthenticationException`을 인자로 받습니다.  
즉, 응답을 직접 다룰 수 있도록 `HttpServletResponse`가 전달되는 구조입니다.

PayMemory에서는 기존 공통 응답 객체인 `ResponseBody`를 그대로 사용하고, `ObjectMapper`로 JSON 문자열로 변환해 응답에 작성했습니다.

이렇게 하면 Security 단계에서 인증 실패가 발생하더라도 기존 API 에러 응답과 동일한 형식을 유지할 수 있습니다.

```json
{
  "statusCode": 401,
  "message": "인증이 필요합니다.",
  "errorCode": 40104
}
```

> Security 단계에서도 프로젝트의 공통 응답 형식을 유지하려면 HttpServletResponse에 직접 JSON을 작성해야 합니다.

## AccessDeniedHandler로 인가 실패 응답 처리하기

인증 실패와 별도로 인가 실패도 처리해야 합니다.

인가 실패는 사용자가 인증은 되었지만 해당 리소스에 접근할 권한이 없을 때 발생합니다.

예를 들어 사용자는 정상적으로 로그인했지만, 관리자 권한이 필요한 API를 호출한 경우입니다.

이 경우에는 401이 아니라 403 응답이 더 적절합니다.

```json
{
  "statusCode": 403,
  "message": "접근 권한이 없습니다.",
  "errorCode": 40301
}
```

Spring Security에서는 인가 실패를 `AccessDeniedHandler`에서 처리합니다.

```java
package site.paymemory.global.security.handler;

import com.fasterxml.jackson.databind.ObjectMapper;
import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;
import lombok.RequiredArgsConstructor;
import org.springframework.security.access.AccessDeniedException;
import org.springframework.security.web.access.AccessDeniedHandler;
import org.springframework.stereotype.Component;
import site.paymemory.global.exception.ErrorCode;
import site.paymemory.global.response.ResponseBody;
import site.paymemory.global.security.exception.SecurityErrorCode;

import java.io.IOException;

@Component
@RequiredArgsConstructor
public class CustomAccessDeniedHandler implements AccessDeniedHandler {

    private final ObjectMapper objectMapper;

    @Override
    public void handle(
            HttpServletRequest request,
            HttpServletResponse response,
            AccessDeniedException accessDeniedException
    ) throws IOException {

        ErrorCode errorCode = SecurityErrorCode.ACCESS_DENIED;
        ResponseBody<Void> body = ResponseBody.error(errorCode);

        response.setStatus(errorCode.getStatus().value());
        response.setCharacterEncoding("UTF-8");
        response.setContentType("application/json");
        response.getWriter().write(objectMapper.writeValueAsString(body));
    }
}
```

구조는 `CustomAuthenticationEntryPoint`와 거의 동일합니다.

다른 점은 실행되는 상황과 사용하는 에러 코드입니다.

```java
ErrorCode errorCode = SecurityErrorCode.ACCESS_DENIED;
```

`AccessDeniedHandler`는 인증 자체가 실패한 상황이 아니라, 인증된 사용자가 필요한 권한을 만족하지 못한 상황을 처리합니다.

따라서 상태 코드는 `403 Forbidden`을 사용했습니다.

Spring Security 공식 문서에서도 `AccessDeniedException`이 발생하면 `AccessDeniedHandler`가 호출된다고 설명합니다.  
`AccessDeniedHandler` 인터페이스 문서 역시 `handle()` 메서드가 `HttpServletResponse`를 받아 실패 응답을 작성할 수 있는 구조임을 보여줍니다.

결국 인증 실패와 인가 실패는 다음처럼 분리됩니다.

```text
401 Unauthorized
→ 인증되지 않은 사용자
→ AuthenticationEntryPoint

403 Forbidden
→ 인증은 되었지만 권한이 부족한 사용자
→ AccessDeniedHandler
```

이렇게 나누어두면 백엔드 응답도 명확해지고, 프론트엔드에서도 상황에 맞는 처리를 하기 쉬워집니다.

## SecurityConfig에 Handler 연결하기

`AuthenticationEntryPoint`와 `AccessDeniedHandler`를 구현했다고 해서 자동으로 Spring Security 예외 처리에 사용되는 것은 아닙니다.

Spring Security 설정에서 명시적으로 연결해야 합니다.

핵심 설정은 다음과 같습니다.

```java
.exceptionHandling(exceptionHandling -> exceptionHandling
        .authenticationEntryPoint(customAuthenticationEntryPoint)
        .accessDeniedHandler(customAccessDeniedHandler)
)
```

PayMemory의 Security 설정 흐름에서는 다음과 같이 연결했습니다.

```java
return http
        .csrf(AbstractHttpConfigurer::disable)
        .cors(Customizer.withDefaults())
        .formLogin(AbstractHttpConfigurer::disable)
        .httpBasic(AbstractHttpConfigurer::disable)
        .sessionManagement(sessionManagement -> sessionManagement
                .sessionCreationPolicy(SessionCreationPolicy.STATELESS)
        )
        .authorizeHttpRequests(authorizeHttpRequests -> authorizeHttpRequests
                .requestMatchers(
                        "/oauth2/**",
                        "/login/oauth2/**",
                        "/users/reissue",
                        "/users/logout"
                ).permitAll()
                .anyRequest().authenticated()
        )
        .exceptionHandling(exceptionHandling -> exceptionHandling
                .authenticationEntryPoint(customAuthenticationEntryPoint)
                .accessDeniedHandler(customAccessDeniedHandler)
        )
        .addFilterBefore(
                new JwtAuthenticationFilter(cookieProvider, tokenProvider),
                UsernamePasswordAuthenticationFilter.class
        )
        .build();
```

PayMemory는 JWT 기반 인증을 사용하므로 서버 세션을 사용하지 않습니다.

```java
.sessionManagement(sessionManagement -> sessionManagement
        .sessionCreationPolicy(SessionCreationPolicy.STATELESS)
)
```

인증이 필요 없는 API는 `permitAll()`로 열어두었습니다.

```java
.requestMatchers(
        "/oauth2/**",
        "/login/oauth2/**",
        "/users/reissue",
        "/users/logout"
).permitAll()
```

그 외 요청은 인증된 사용자만 접근할 수 있도록 설정했습니다.

```java
.anyRequest().authenticated()
```

이제 인증이 필요한 요청에서 인증 정보가 없으면 `CustomAuthenticationEntryPoint`가 실행됩니다.

반대로 인증 정보는 있지만 필요한 권한이 부족한 경우에는 `CustomAccessDeniedHandler`가 실행됩니다.

Spring Security의 `ExceptionHandlingConfigurer` 문서에서도 `authenticationEntryPoint()`는 사용할 `AuthenticationEntryPoint`를 설정하고, `accessDeniedHandler()`는 사용할 `AccessDeniedHandler`를 지정한다고 설명합니다.

즉, 이 설정은 단순히 클래스를 등록하는 작업이 아니라 Spring Security의 인증/인가 실패 처리 지점을 프로젝트의 공통 응답 방식에 맞게 교체하는 작업입니다.

## JWT 인증 필터에서 함께 고려한 점

이번 글의 중심은 JWT 필터 자체가 아닙니다.

핵심은 다음 질문입니다.

```text
왜 Spring Security 인증/인가 실패는 GlobalExceptionHandler에서 잡히지 않았을까?
```

다만 이 문제를 해결하면서 JWT 인증 필터에서도 몇 가지 함께 정리한 부분이 있습니다.

PayMemory에서는 Access Token을 HttpOnly Cookie로 내려주고, 요청마다 Cookie에서 Access Token을 꺼내 인증을 수행합니다.

JWT 인증 필터의 핵심 흐름은 다음과 같습니다.

```java
try {
    cookieProvider.getAccessToken(request)
            .ifPresent(this::authenticate);
} catch (GlobalException e) {
    SecurityContextHolder.clearContext();
}

filterChain.doFilter(request, response);
```

Access Token이 존재하면 `authenticate()`를 호출해 인증 객체를 만들고, `SecurityContext`에 저장합니다.

토큰 파싱이나 검증 과정에서 예외가 발생하면 `SecurityContextHolder.clearContext()`를 호출해 인증 정보를 비웁니다.

여기서 한 가지 주의할 점이 있습니다.

JWT 필터 안에서 발생한 예외를 무조건 `AuthenticationEntryPoint`가 처리해준다고 생각하면 안 됩니다.  
커스텀 필터의 위치가 `ExceptionTranslationFilter`보다 앞이라면, 해당 필터에서 직접 던진 예외는 `ExceptionTranslationFilter`가 잡지 못할 수 있습니다.

그래서 이번 구현에서는 토큰 검증 실패 시 예외를 다시 던져 `GlobalExceptionHandler`로 보내려 하지 않았습니다.  
대신 `SecurityContext`를 비우고 다음 필터 흐름으로 넘겼습니다.

이후 인증이 필요한 API라면 Spring Security가 인증되지 않은 요청으로 판단하고, 설정된 `AuthenticationEntryPoint`를 통해 401 응답을 내려주게 됩니다.

인증 객체를 설정하는 코드는 다음과 같습니다.

```java
private void authenticate(String accessToken) {

    Long userId = tokenProvider.getUserId(accessToken);

    UsernamePasswordAuthenticationToken authentication =
            new UsernamePasswordAuthenticationToken(
                    userId,
                    null,
                    Collections.emptyList()
            );

    SecurityContext securityContext = SecurityContextHolder.createEmptyContext();
    securityContext.setAuthentication(authentication);
    SecurityContextHolder.setContext(securityContext);
}
```

여기서도 개선한 부분이 있습니다.

기존에는 다음처럼 현재 `SecurityContext`를 가져와 바로 수정하는 방식을 사용할 수 있습니다.

```java
SecurityContextHolder.getContext().setAuthentication(authentication);
```

하지만 이번에는 새 `SecurityContext`를 만들어 인증 정보를 설정했습니다.

```java
SecurityContext securityContext = SecurityContextHolder.createEmptyContext();
securityContext.setAuthentication(authentication);
SecurityContextHolder.setContext(securityContext);
```

Spring Security 공식 문서에서도 사용자가 인증되었음을 나타내는 가장 단순한 방법으로 다음 흐름을 안내합니다.

```java
SecurityContext context = SecurityContextHolder.createEmptyContext();
Authentication authentication = ...
context.setAuthentication(authentication);
SecurityContextHolder.setContext(context);
```

그리고 기존 context에 바로 `setAuthentication()`을 호출하는 대신 새 `SecurityContext` 인스턴스를 만들라고 설명합니다.  
그 이유는 여러 스레드 간 race condition을 피하기 위해서입니다.

따라서 `SecurityContextHolder.createEmptyContext()`를 사용한 것은 단순한 취향의 문제가 아니라, Spring Security가 안내하는 방식에 맞춘 선택입니다.

또 하나 고려한 점은 JWT 필터 등록 방식입니다.

JWT 필터에는 `@Component`를 붙이지 않고, `SecurityConfig`에서 직접 생성해 등록했습니다.

```java
.addFilterBefore(
        new JwtAuthenticationFilter(cookieProvider, tokenProvider),
        UsernamePasswordAuthenticationFilter.class
)
```

이유는 필터 중복 실행 가능성을 줄이기 위해서입니다.

Spring Boot 공식 문서에 따르면 Servlet 애플리케이션에서 Spring Bean으로 등록된 `Filter`는 embedded servlet container에 자동 등록됩니다.  
또한 기본적으로 Filter는 `/*`에 매핑됩니다.

따라서 JWT 필터를 `@Component`로 등록하면 일반 Servlet Filter Chain에 자동 등록될 수 있습니다.  
그 상태에서 `addFilterBefore()`로 Spring Security Filter Chain에도 등록하면 같은 필터가 의도치 않게 두 번 실행될 여지가 생깁니다.

이번 JWT 필터는 Spring Security 인증 흐름 안에서만 실행되면 충분했습니다.

그래서 `@Component`로 등록하지 않고, `SecurityConfig`에서 명시적으로 Security Filter Chain에만 추가했습니다.

정리하면 JWT 필터에서 고려한 내용은 다음과 같습니다.

```text
1. Access Token은 Cookie에서 꺼냅니다.
2. 토큰이 유효하면 Authentication을 만들어 SecurityContext에 저장합니다.
3. 토큰 검증 실패 시 SecurityContext를 비웁니다.
4. 필터 단계 예외를 GlobalExceptionHandler로 보내려 하지 않습니다.
5. 인증 실패 응답은 AuthenticationEntryPoint에서 처리합니다.
6. JwtAuthenticationFilter는 @Component로 등록하지 않고 SecurityConfig에서 직접 등록합니다.
7. SecurityContextHolder.createEmptyContext()로 새 Context를 만들어 설정합니다.
```

이렇게 정리하고 나니 각 구성 요소의 책임이 더 분명해졌습니다.

JWT 필터는 인증 정보를 만들어 `SecurityContext`에 넣는 역할에 집중합니다.  
인증 실패 응답은 `AuthenticationEntryPoint`가 담당합니다.  
인가 실패 응답은 `AccessDeniedHandler`가 담당합니다.  
Controller 이후의 비즈니스 예외는 기존처럼 `GlobalExceptionHandler`가 담당합니다.

## 정리

처음에는 인증 실패도 `GlobalExceptionHandler`에서 처리될 것이라고 생각했습니다.

하지만 실제로 Access Token이 없는 상태에서 인증이 필요한 API를 호출해보니, 기존 공통 응답 형식이 내려오지 않았습니다.

문제는 예외가 발생한 위치였습니다.

`GlobalExceptionHandler`는 Controller 이후의 예외를 처리하는 데 적합합니다.  
반면 Spring Security 인증/인가 실패는 Controller에 도달하기 전에 Filter Chain에서 발생할 수 있습니다.

따라서 Security 단계의 실패 응답은 Spring Security가 제공하는 처리 지점에서 만들어야 합니다.

```text
Controller 이후 예외
→ GlobalExceptionHandler

Security 인증 실패
→ AuthenticationEntryPoint

Security 인가 실패
→ AccessDeniedHandler
```

그리고 Security Filter Chain 내부에서는 `ResponseEntity`를 반환하는 방식이 아니라, `HttpServletResponse`에 직접 응답을 작성해야 합니다.

PayMemory에서는 `ObjectMapper`를 사용해 기존 공통 응답 객체인 `ResponseBody`를 JSON 문자열로 변환했습니다.  
덕분에 Security 단계의 실패 응답도 프로젝트의 공통 응답 형식에 맞출 수 있었습니다.

마지막으로 이번 작업에서 배운 점은 다음과 같습니다.

```text
GlobalExceptionHandler는 모든 예외를 처리하는 만능 Handler가 아닙니다.
Spring Security Filter Chain에서 발생한 인증/인가 실패는 Controller까지 도달하지 않을 수 있습니다.
인증 실패는 AuthenticationEntryPoint, 인가 실패는 AccessDeniedHandler에서 처리해야 합니다.
```
