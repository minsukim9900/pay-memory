# Mockito 없이 단위 테스트를 작성하기 위해 UserRepositoryPort를 도입한 과정

`/users/me` API를 구현하면서 느낀 오늘의 회고록입니다.

### 시작은 단순한 /users/me API

`/users/me` API는 현재 로그인한 사용자의 기본 정보를 조회하는 기능입니다.

응답으로는 다음 정보를 내려줍니다.

- userId
- email
- nickname
- profileImageUrl

또한 탈퇴한 사용자는 조회 대상에서 제외하도록 구현했습니다.

처음에는 일반적인 Spring Data JPA Repository를 사용했습니다.

```java
public interface UserRepository extends JpaRepository<User, Long> {

    Optional<User> findBySocialId(String socialId);

    Optional<User> findByIdAndDeletedAtIsNull(Long id);
}
```

Service 역시 자연스럽게 Repository를 직접 의존하고 있었습니다.

```java
@Service
@RequiredArgsConstructor
@Transactional(readOnly = true)
public class UserService {

    private final UserRepository userRepository;

    public UserInfoResponse findMe(Long userId) {

        User user = userRepository.findByIdAndDeletedAtIsNull(userId)
                .orElseThrow(() -> new GlobalException(UserErrorCode.USER_NOT_FOUND));

        return UserInfoResponse.from(user);
    }
}
```

API도 정상적으로 동작하고, 구현 자체도 매우 단순합니다.

하지만 Service 테스트 코드를 작성하면서 다른 고민이 생겼습니다.

> **Mockito 없이 어떻게 테스트할까?**

Mockito를 사용하면 충분히 테스트를 작성할 수 있습니다.

하지만 이번에는 Mocking 프레임워크에 의존하지 않고,
서비스의 비즈니스 로직만 검증하는 **순수 단위 테스트**를 작성해보고 싶었습니다.

그래서 다시 생각해 보니 문제는 테스트 도구가 아니었습니다.

처음 구조에서는 Service 테스트 코드를 작성할 때 자연스럽게 몇 가지 선택지가 생깁니다.

- Mockito로 Repository를 Mocking 한다.
- Spring Context를 띄운다.
- 실제 DB를 연결해 통합 테스트처럼 작성한다.

![UserService 의존성 변화 비교](https://velog.velcdn.com/images/mindoli/post/fc4d50ba-141a-4bd1-952a-d2b0407ae855/image.png)

순수 단위 테스트 코드 작성이 어려웠던 이유는 Mockito가 없어서가 아니었습니다.
**Service가 `UserRepository`를 의존하고 있었기 때문이었습니다.**

운영 환경에서는 JPA Repository가 필요합니다. 반면 테스트에서는 DB없이 동작하는 Map 기반 저장소만 있으면 충분하다고 생각했습니다.

그런데 Service가 `UserRepository`에 의존하면 테스트에서 다른 구현체를 주입하기 어렵습니다.

### 그래서 UserRepositoryPort를 도입

![운영 환경과 테스트 환경의 구현체 분리 구조](https://velog.velcdn.com/images/mindoli/post/cee3b52a-9436-4e3b-82fe-580aa184a1da/image.png)



Service가 실제로 필요한 것은 JPA Repository 자체가 아닙니다. 필요한 것은 **"사용자를 조회하는 기능"** 하나였습니다.

그래서 필요한 기능만 인터페이스로 분리했습니다.

```java
public interface UserRepositoryPort {

    Optional<User> findByIdAndDeletedAtIsNull(Long id);
}
```

그리고 `UserRepository`가 이 Port를 구현하도록 변경했습니다.

```java
public interface UserRepository extends JpaRepository<User, Long>, UserRepositoryPort {

    Optional<User> findBySocialId(String socialId);

    @Override
    Optional<User> findByIdAndDeletedAtIsNull(Long id);
}
```

이렇게 변경한 이후 **Service는 어떤 구현체가 사용되는지 알 필요가 없어졌습니다.**

필요한 기능만 제공한다면 어떤 구현체든 사용할 수 있는 구조가 되었습니다.

운영 환경에서는 JPA Repository가 그대로 동작하고, 테스트 환경에서는 Fake 구현체를 사용할 수 있게 되었습니다.

이 과정에서 운영 코드와 테스트 코드의 역할을 분리할 수 있었습니다.

### FakeUserRepositoryPort로 Map 기반 테스트 코드 작성

![UserRepositoryPor 도입 전후 테스트 방식 비교](https://velog.velcdn.com/images/mindoli/post/7fb78caf-977a-4081-9bb9-c895b8377603/image.png)



Port를 만들고 나니 테스트 코드는 훨씬 단순해졌습니다.
테스트에서는 실제 DB 대신 Map을 사용하는 Fake 구현체를 만들었습니다.

```java
public class FakeUserRepositoryPort implements UserRepositoryPort {

    private final Map<Long, User> users = new HashMap<>();

    @Override
    public Optional<User> findByIdAndDeletedAtIsNull(Long id) {

        return Optional.ofNullable(users.get(id))
                .filter(user -> user.getDeletedAt() == null);
    }
}
```

덕분에 Spring Context도 필요 없어졌으며, Mockito도 필요 없어졌습니다. DB도 필요 없이 순수한 테스트 코드를 작성할 수 있었습니다.

### UserRepositoryPort를 도입하며 느낀 점

이번 작업의 목표는 API를 하나 만드는 것이 아니라 **Mockito와 Spring Context 없이 Service를 테스트할 수 있는 구조를 만드는 것**이었습니다.

`UserRepositoryPort`를 도입하면서 운영 환경과 테스트 환경이 자연스럽게 분리되었습니다.

Service는 더 이상 Spring Data JPA Repository에 직접 의존하지 않고,
필요한 기능만 정의한 인터페이스에 의존하게 되었습니다.

물론 모든 상황에서 반드시 Port를 도입해야 한다고 생각하지 않습니다.
프로젝트의 규모나 테스트 전략에 따라 충분히 다른 선택을 할 수 있습니다.

서비스 계층이 어떤 객체에 의존해야 하는지, 그리고 테스트 가능한 구조를 어떻게 만들 수 있는지 고민하는 시간이었습니다.

앞으로도 기능 구현에만 집중하기보다, 운영 코드와 테스트 코드가 함께 유지보수하기 쉬운 구조인지 한 번 더 고민해 보려고 합니다.
